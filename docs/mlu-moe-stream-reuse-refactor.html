Executive decision

结论摘要

YES可行，建议推进

采用 ModelStreamRegistry，作用域绑定模型实例

registry 由 ModelContext 共享持有，组件按照执行角色调用 get()。 每个角色第一次被请求时创建 stream，后续返回同一实例；独立模型之间互不共享。

Target architecture

目标架构：按执行角色注册模型级 stream

01

模型作用域

每个根 ModelContext 创建一个 registry。context 的普通复制及派生 context 共享该 registry。

02

惰性初始化

仅角色第一次被组件请求时创建 stream；没有使用该并行角色的模型不会创建额外资源。

03

强类型接口

使用 ExecutionStreamRole，不使用字符串 key 或组件名称；MoE 与 Attention 共享同一种语言。

04

线程安全

get(role) 使用锁保护，保证并发构建层时每个角色也只产生一条 stream。

05

设备一致

registry 构造时绑定 device，调用方只提供 role，从接口上消除跨设备误取的可能。

06

RAII 销毁

context/registry/stream 的 shared ownership 链随模型释放，无进程级缓存、无悬挂 key、无额外清理 API。

Suggested API

建议接口草案

类型可以放在 framework/platform 可接受的低层位置，避免通用 framework 反向依赖具体 FusedMoE 或 Attention 实现。 registry 构造时绑定模型 device，角色使用强类型枚举，名称需遵守项目 RULES.md 的函数下划线数量约束。 

enum class ExecutionStreamRole : int8_t {
  COMMUNICATION,
  AUXILIARY_COMPUTE,
};

class ModelStreamRegistry final {
 public:
  explicit ModelStreamRegistry(const torch::Device& device);

  std::shared_ptr<Stream> get(ExecutionStreamRole role);

 private:
  torch::Device device_;
  std::mutex mutex_;
  std::unordered_map<ExecutionStreamRole,
                     std::shared_ptr<Stream>> streams_;
};

class ModelContext {
 public:
  const std::shared_ptr<ModelStreamRegistry>& stream_registry() const;

 private:
  std::shared_ptr<ModelStreamRegistry> stream_registry_;
};

MoE 和 Attention 按执行语义获取，而不是按组件名获取：

const auto& registry = context.stream_registry();
const auto& comm_stream =
    registry->get(ExecutionStreamRole::COMMUNICATION);
const auto& aux_compute_stream =
    registry->get(ExecutionStreamRole::AUXILIARY_COMPUTE);

sparse_moe_ = register_module(
    "mlp",
    SparseMoEBlock(model_args,
                   quant_args,
                   parallel_args,
                   options,
                   comm_stream,
                   aux_compute_stream));

// Attention SP can reuse the same communication role when its schedule
// guarantees that it does not need to overlap with another role consumer.
const auto& sp_comm_stream =
    registry->get(ExecutionStreamRole::COMMUNICATION);
共享 registry 不等于强制共享物理 stream MoE routed communication 与 Attention SP communication 只有在调度上不会同时执行时，才共同使用 COMMUNICATION。 如果未来确实需要并发，应增加新的语义角色，而不是用 MOE_*/ATTENTION_* 组件名称提前固化边界。

Migration plan

建议分三步迁移

1

建立资源边界

新增强类型 registry 和 role；由根 ModelContext 创建，确保 copy、with_parallel_args() 和 with_quant_args() 共享。

2

下沉获取位置

让实际构建 MoE 的 decoder/sparse block 按角色获取 stream；先保持 FusedMoEImpl 对两条 stream 的显式依赖。

3

删除传播脚手架

删除 MoEDecoderLayerFactory、模型层 lambda、MTP 中只为 stream 增加的 factory overload，以及相应构造参数。

Guardrails

风险与设计边界

!

Context 派生丢失 registry

当前 with_parallel_args()/with_quant_args() 会构造新 context；必须显式复制 registry，或重构为天然共享的 model scope state。

!

层次依赖反转

不要让 framework header include layers/mlu/fused_moe.h 或 Attention header。registry 和 role 应位于 platform/framework 可接受的低层位置。

!

锁覆盖创建过程

需要保证只发布完整构造的 stream。角色获取只发生在 layer 初始化而非 forward 热路径，简单互斥锁已经足够；返回 shared_ptr 值可避免容器扩容导致引用失效。

!

Graph capture

stream 必须在模型/层初始化阶段确定，不能在首次 forward 或 capture 中才创建；lazy 指“首次组件构建时请求角色”，不是“首次执行”。

!

MTP 作用域

需要确认 target model 与独立 draft/MTP model 是否应视作不同模型实例；默认建议各自拥有 registry，除非生命周期明确属于同一模型对象。

!

角色不能等同组件

优先使用 COMMUNICATION / AUXILIARY_COMPUTE 等执行语义。只有确有并发冲突时才拆分新角色，避免退化为 MOE_* / ATTENTION_* 名称列表。

历史证据 本分支提交 c800fb20 曾通过通用 ModelResourceRegistry 实现 FusedMoEStreams::get_or_create(context)，说明“组件从 context 获取模型级资源”的路径已被代码验证。新方案把 registry 收窄到模型执行 stream，并以强类型 role 替代字符串 key/type erasure。
Final recommendation

最终建议

推进 ModelStreamRegistry；按执行角色跨 MoE 与 Attention 复用

  1. 保证 registry 是 per model instance，不是 per process 或 per device。
  2. 构造时绑定 device，在 layer 初始化阶段按 role lazy create。
  3. ModelContext 的所有派生副本共享同一 registry。
  4. 第一阶段保留 FusedMoEImpl 显式接收两条角色 stream，控制重构范围。
  5. 相同 role 是否复用物理 stream 必须由调度互斥关系决定，而不是由组件名称决定。
