KV Cache storage path explained

内存已经双向，为什么 SSD 还要单独接？

因为“双向”只说明内存地址之间能来回搬运。Mooncake 把副本淘汰到 LOCAL_DISK 后，必须先调用 RealClient 把文件读出来，才能继续搬运。

一句话结论
接了仓库，不等于接了仓库的地下室。

Mooncake 管理 MEMORY 和 SSD；但调用方使用的接口必须能够处理两种副本。 原始 xLLM 只闭环了 MEMORY，修复后才闭环 LOCAL_DISK 回读。

先分清三件事

三个能力，不是一回事

最容易混淆的是：Mooncake “支持 SSD”属于存储系统能力；xLLM “能从 SSD 恢复”属于客户端接入能力。

1

2

Mooncake 内存传输

Host 与 Mooncake MEMORY 副本之间读写，目标是可寻址的内存。

3

SSD 回读

LOCAL_DISK 没有可直接 memcpy/RDMA 的地址，RealClient 必须先读取文件。

原本、修复后、其他框架

vLLM/SGLang 没有自己实现 SSD 文件系统；它们接入完整的 MooncakeDistributedStore / RealClient 接口。

实现 Mooncake MEMORY LOCAL_DISK-only 回读 关键接口 结论
原始 xLLM ● 支持读写 ● 不保证 Client::BatchGet 内存副本消失后可能恢复失败
修复后 xLLM ● 支持读写 ● 支持回读 RealClient + batch_get_into_multi_buffers MEMORY 与 LOCAL_DISK 均可恢复
vLLM ● 支持 ● 支持 MooncakeStoreConnector 统一 Store Get，Mooncake 内部分派
SGLang ● 支持 ● 支持 HiCache Mooncake backend 统一 Store Get，Mooncake 内部分派
Mooncake 旧 DISK / DFS — ● 不属于本次范围 后端与配置相关 不能由 LOCAL_DISK 修复类推
最终记忆点

“双向”描述方向；“闭环”描述覆盖的存储层。

原始 xLLM 的双向链路只覆盖 HBM、Host、Mooncake MEMORY。修复新增的是 LOCAL_DISK-only 的恢复闭环，而不是重新实现一个 SSD 管理器。

生效前提

  • Mooncake Master 开启 SSD offload。
  • 持有 SSD 的 RealClient 配置可写的本地路径。
  • 客户端使用兼容版本和完整 Store/RealClient 回读接口。
  • NPU/MLU 的 Host ↔ HBM 搬运路径本身可用。
