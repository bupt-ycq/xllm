2D DMA 和
Batch Memcpy
到底差在哪？

两者都能“一次 API 调用复制多段数据”，但给 DMA 引擎的任务描述完全不同： Batch 提交一张任务清单，2D DMA 提交一条固定步长公式。

一句话答案：地址越规则，越适合 2D DMA；地址越随机，越需要 Batch Memcpy。

01 / DMA BASICS

先把 DMA 放回整条链路里

CPU 不亲自逐字节搬数据，而是把“从哪里、到哪里、搬多少”交给 DMA 引擎。CPU 的主要成本是准备描述信息并提交。

02 / BATCH MEMCPY

Batch：提交一张“逐项任务清单”

cnMemcpyBatchAsync 接收多组源地址、目标地址和字节数。它能处理任意映射，是最通用的兜底路径。

它擅长什么？

KV block id 无规律、源和目标映射随机、每段大小可能不同。这时没法用一条 pitch 公式概括。

N个独立 descriptor

“Batch”不等于“一次大 memcpy”

虽然调用一次 API，但参数里仍携带 N 组地址。驱动和 DMA 引擎仍需解析这些 descriptor。

它的成本在哪里？

CPU 构造三个数组、驱动读取 descriptor、设备逐项解析。数据越碎，元数据相对成本越明显。

03 / 2D DMA

2D：提交一条“固定步长公式”

cnMemcpy2DAsync 把一批等宽、等步长的行看作一个二维矩形。DMA 引擎用 width、height 和 pitch 自动生成每行地址。

width

每一行真正复制的有效字节数。

pitch

本行起始地址到下一行起始地址的距离，可大于 width。

height

有多少行，也就是本次可覆盖多少个规则 descriptor。

05 / COST MODEL

优化的重点是元数据与提交开销

2D DMA 不会神奇地减少有效数据字节数；它减少的是地址数组、descriptor 解析和多段任务管理。下面是概念示意，不是实测 benchmark。

06 / XLLM DISPATCH

xLLM 怎样决定走哪条路径？

代码扫描相邻 descriptor 的地址变化：同 storage、同字节数、源和目标方向一致，并且 stride 稳定，才有资格转成 2D DMA。

07 / CODE MAP

对应到当前实现，大致是这段逻辑

代码先识别一段 run，再选择 extent、2D 或 batch。2D 提交前会先 flush 已累积的 batch，保持原始复制顺序。

while (begin < descriptors.size()) {
  run = find_direct_copy_run(descriptors, begin);

  if (run.kind == TWO_DIMENSIONAL) {
    flush_batch();
    cnMemcpy2DAsync(
        dst_addr,
        run.dst_pitch,
        src_addr,
        run.src_pitch,
        row_bytes,       // width
        run.count,       // height
        queue);
    begin += run.count;
    continue;
  }

  if (run.kind == EXTENT) {
    bytes = row_bytes * run.count;
  } else {
    bytes = row_bytes;   // batch fallback
  }
  batch.push(src, dst, bytes);
}

为什么 2D 前要 flush batch？

如果前面已有随机 descriptor，必须先提交它们，再提交 2D，才能保持调用者给出的顺序和队列语义。

为什么比较 storage？

仅靠虚拟地址碰巧等差不够安全。同一 run 的 tensor 必须来自相同源 storage 和目标 storage。

为什么 reverse 需要特别处理？

2D API 使用正 pitch。反向 descriptor 序列需要从最低地址那一行开始，再用正 pitch 覆盖整段。

记住这四点就够了

  • Batch Memcpy：一次调用携带 N 条独立 copy 清单，最通用。
  • 2D DMA：一次调用携带一条 width / height / pitch 公式，适合规则地址。
  • 2D 优化减少的是 descriptor 和提交管理成本，不减少有效数据字节数。
  • 规则不成立时必须回退 Batch；错误使用 2D 会复制到错误地址。
结论

对 xLLM KV Cache 来说：连续就合并，固定 stride 就 2D，剩下全部 Batch。
